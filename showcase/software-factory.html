Agentic engineering

Software factory: a gated AI engineering pipeline

AI coding agents are fast and confident, and confidence is not evidence. The factory gives agents a disciplined process: every stage must pass a gate that re-runs real commands and re-reads real files before work moves on.

StackNode.js (zero runtime dependencies), Claude Code, GitHub Actions
Runs onAny git repository; CLI, local dashboard, or a GitHub issue label
StatusWorking tool with its own CI, CodeQL and secret scanning

The problem

Agents that say done before they are

Coding agents will happily report that tests pass, that a review approved a change, or that nothing else was touched. In a regulated environment, “the model said so” is not an acceptable control. The goal was a pipeline where the evidence for every step is produced by the pipeline itself, and where a person still makes the final call.

What was built

Three parts that work alone or together

  • Project templates: four starters (single-file static site, full-stack React and Fastify, Node service, Python FastAPI service) that ship with strict linting, typed code, coverage-gated tests, CI, CodeQL, secret scanning, Dependabot, release automation and container builds from the first commit.
  • An agent kit for Claude Code: fifteen specialised subagents in two crews, slash commands for each stage, nineteen skills (test-driven development, secure coding, synthetic data and more) and guard hooks that block destructive commands, writes to credentials, and real-format identifiers.
  • The pipeline: spec, plan, build, test, review, inspect and ship, with retries that feed each gate's exact failure back to the agent, a live local dashboard, per-stage spend caps, and a GitHub Action that runs when an issue is labelled.

Approach

Gates, not good intentions

Spec→Plan→Build→Test→Review→Inspect→Pull request
  • Deterministic gates. A plan fails unless every acceptance criterion from the spec appears in its tasks. A build fails unless tests were added and lint, typecheck and build pass. A review fails on any blocker, any secret or identifier in a changed file, or a file changed outside its scope.
  • A second pair of eyes. The review stage can run on a different model from the one that wrote the code, and a review that requests changes rewinds the run to build.
  • An inspector before release. It re-verifies the candidate itself: earlier gates really passed, checks pass when re-run, coverage did not drop, risky areas such as migrations, auth and workflows are flagged. It can hold a release; only a person can override a hold, and that override is audited.
  • Least privilege in CI. The agent job has read-only permissions and no write token; a separate job with no agent applies the reviewed patch and opens the pull request. Issue text is treated as untrusted input.
  • Provider-neutral. Each stage can route to Claude Code, the Anthropic API or any OpenAI-compatible endpoint, with fallbacks and escalation on retry.
  • Self-improvement with a citation gate. A steward reads the run history, drafts improvement proposals, and code rejects any claim that does not cite a real recorded fact. Proposals wait for approval by default.

What it shows

AI you can audit

The factory is a working answer to the question every health system asks about generative AI: how do you let it do real work without trusting it blindly? The answer here is to separate generation from verification, keep a person on the merge button, cap the spend, and write down the evidence for every decision where a reviewer can read it.

Nothing merges itself. Every pull request carries its acceptance criteria, gate results, review verdict and cost for a human to approve.
